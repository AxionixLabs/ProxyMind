# 技能创建器

本技能用于指导高质量技能的创建与维护。

## 关于技能

技能是模块化且自包含的目录，通过提供专业知识、工作流和工具来扩展 Mind 的能力。可以把技能看作特定领域或任务的“入门指南”：它们让通用代理获得模型本身无法完整掌握的过程性知识，成为专用代理。

### 技能提供的能力

1. 专用工作流：特定领域的多步骤流程
2. 工具集成：处理特定文件格式或 API 的说明
3. 领域知识：组织内部知识、数据结构和业务逻辑
4. 随附资源：用于复杂、重复任务的脚本、参考资料和资产

## 核心原则

### 保持精简

上下文窗口是共享资源。技能会与系统提示、对话历史、其他技能的元数据和用户请求共同占用上下文。

**默认假设：Mind 已具备很强的通用能力。** 只补充 Mind 尚不了解的内容。逐段判断：“Mind 真的需要这段说明吗？”以及“这段内容值得占用这些令牌吗？”

优先使用简洁示例，不写冗长说明。

### 设置合适的自由度

根据任务的脆弱性和可变性选择说明的具体程度：

**高自由度（文字说明）**：存在多种正确方案、决策依赖上下文或适合使用启发式方法时采用。

**中自由度（伪代码或带参数脚本）**：存在推荐模式、允许一定变化或行为受配置影响时采用。

**低自由度（明确脚本和少量参数）**：操作脆弱、容易出错、强依赖一致性或必须遵循固定顺序时采用。

可以把 Mind 想象成在路径中探索：悬崖之间的窄桥需要明确护栏，而开阔地带可以允许多种走法。

### 技能结构

每个技能都包含必需的 `SKILL.md`，并可包含随附资源：

```text
skill-name/
├── SKILL.md（必需）
│   ├── YAML 前置元数据 frontmatter（必需）
│   │   ├── name:（必需）
│   │   └── description:（必需）
│   └── Markdown 使用说明（必需）
└── 随附资源（可选）
    ├── scripts/          - 可执行代码（Python、Bash 等）
    ├── references/       - 按需载入上下文的参考资料
    └── assets/           - 输出中使用的文件（模板、图标、字体等）
```

#### SKILL.md（必需）

每个 `SKILL.md` 包含：

- **前置元数据 frontmatter（YAML）**：包含 `name` 和 `description`。Mind 只依靠这些字段判断是否使用技能，因此必须清晰、完整地说明技能能力和触发场景。
- **正文（Markdown）**：技能的使用说明与操作指南。只有技能触发后才会载入。

#### 随附资源（可选）

##### 脚本（`scripts/`）

为需要确定性、可靠性或会重复编写的任务提供可执行代码。

- **适用情况**：同一段代码会反复编写，或任务需要稳定、可复现的执行结果
- **示例**：用于旋转 PDF 的 `scripts/rotate_pdf.py`
- **优势**：节省令牌、结果稳定，并且可以不载入上下文直接执行
- **注意**：Mind 仍可能需要读取脚本，以便修改代码或适配运行环境

##### 参考资料（`references/`）

按需载入上下文、用于辅助 Mind 决策和执行的文档。

- **适用情况**：Mind 执行任务时需要查阅详细资料
- **示例**：财务数据结构 `references/finance.md`、保密协议模板 `references/mnda.md`、公司政策 `references/policies.md`、API 说明 `references/api_docs.md`
- **用途**：数据库结构、API 文档、领域知识、公司政策和详细工作流
- **优势**：保持 `SKILL.md` 精简，只在 Mind 判断必要时载入
- **最佳实践**：文件超过一万词时，在 `SKILL.md` 中提供建议的搜索模式
- **避免重复**：同一信息只放在 `SKILL.md` 或参考资料中的一处。详细内容优先放入参考资料；`SKILL.md` 只保留必要流程和核心指引。

##### 资产（`assets/`）

不用于载入上下文，而是直接用于最终输出的文件。

- **适用情况**：技能需要把文件用于最终交付物
- **示例**：品牌图片 `assets/logo.png`、演示模板 `assets/slides.pptx`、前端模板 `assets/frontend-template/`、字体 `assets/font.ttf`
- **用途**：模板、图片、图标、样板代码、字体和示例文档
- **优势**：将输出资源与说明文档分开，Mind 无需将文件载入上下文即可使用

#### 不应包含的内容

技能只应包含直接支持其功能的必要文件。不要创建无关文档或辅助文件，例如：

- `README.md`
- `INSTALLATION_GUIDE.md`
- `QUICK_REFERENCE.md`
- `CHANGELOG.md`

技能目录只保留代理完成任务需要的信息，不记录创建过程、安装测试步骤或面向最终用户的额外说明，以免增加混乱和上下文负担。

### 渐进式披露

技能通过三个层级控制上下文用量：

1. **元数据（`name` 和 `description`）**：始终位于上下文中，建议约一百词
2. **`SKILL.md` 正文**：技能触发后载入，建议少于五千词
3. **随附资源**：Mind 按需读取；脚本可直接执行，无需载入上下文

#### 渐进式披露模式

`SKILL.md` 应只保留核心内容并控制在 500 行以内。接近限制时，将详细内容拆到独立文件，并在 `SKILL.md` 中明确说明何时读取这些文件。

**核心原则：** 一个技能支持多种变体、框架或选项时，`SKILL.md` 只保留通用工作流和选择依据，将具体模式、示例和配置放入参考资料。

**模式一：高层指南配合参考资料**

```markdown
# PDF 处理

## 快速开始

使用 pdfplumber 提取文本：
[代码示例]

## 高级功能

- **填写表单**：完整说明见 [FORMS.md](FORMS.md)
- **API 参考**：所有方法见 [REFERENCE.md](REFERENCE.md)
- **示例**：常用模式见 [EXAMPLES.md](EXAMPLES.md)
```

Mind 只在需要时读取 `FORMS.md`、`REFERENCE.md` 或 `EXAMPLES.md`。

**模式二：按领域组织**

技能包含多个领域时，按领域拆分内容，避免载入无关上下文：

```text
bigquery-skill/
├── SKILL.md（概览和导航）
└── references/
    ├── finance.md（收入和计费指标）
    ├── sales.md（商机和销售管道）
    ├── product.md（API 用量和功能）
    └── marketing.md（营销活动和归因）
```

用户询问销售指标时，Mind 只读取 `sales.md`。

支持多个框架或实现方式时，也按变体组织：

```text
cloud-deploy/
├── SKILL.md（工作流和服务商选择）
└── references/
    ├── aws.md（AWS 部署模式）
    ├── gcp.md（GCP 部署模式）
    └── azure.md（Azure 部署模式）
```

用户选择 AWS 时，Mind 只读取 `aws.md`。

**模式三：按条件展开细节**

正文只展示基础内容，通过链接提供高级说明：

```markdown
# DOCX 处理

## 创建文档

使用 docx-js 创建文档。参见 [DOCX-JS.md](DOCX-JS.md)。

## 编辑文档

简单修改可以直接编辑 XML。

**修订模式**：参见 [REDLINING.md](REDLINING.md)
**OOXML 细节**：参见 [OOXML.md](OOXML.md)
```

只有用户需要相应功能时，Mind 才读取 `REDLINING.md` 或 `OOXML.md`。

**重要要求：**

- **避免深层嵌套引用**：参考资料与 `SKILL.md` 之间只保持一层关系，所有参考文件都应由 `SKILL.md` 直接链接。
- **为长文件提供结构**：参考文件超过 100 行时，在顶部添加目录，便于 Mind 预览整体范围。

## 技能创建流程

按以下步骤创建技能：

1. 通过具体示例理解技能需求
2. 规划可复用内容，包括脚本、参考资料和资产
3. 运行 `init_skill.py` 初始化技能
4. 编写资源和 `SKILL.md`
5. 运行 `quick_validate.py` 验证技能
6. 根据实际使用结果迭代

除非某一步明确不适用，否则按顺序执行。

### 技能命名

- 只使用小写字母、数字和连字符，将用户提供的标题规范化为连字符形式，例如 `plan-mode`。
- 名称不超过 64 个字符。
- 优先使用简短、以动词开头且能描述动作的名称。
- 以工具名作为命名空间能提高辨识度或触发准确性时采用，例如 `gh-address-comments`、`linear-address-issue`。
- 技能目录名必须与技能名称完全一致。

### 第一步：通过具体示例理解技能

仅在使用方式已经非常明确时跳过本步骤。即使修改现有技能，具体示例仍有助于确认范围。

通过真实示例明确技能应支持的能力。示例可以来自用户，也可以先由代理提出，再请用户确认。

例如，创建图像编辑技能时，可以确认：

- “图像编辑技能需要支持哪些功能？编辑、旋转，还是其他操作？”
- “可以提供几个使用这个技能的例子吗？”
- “我想到的请求包括‘去除红眼’和‘旋转图片’，还需要支持哪些请求？”
- “用户会如何表达，才应该触发这个技能？”

不要在一条消息里提出过多问题。先确认最重要的信息，再按需追问。能够清晰描述技能用途后结束本步骤。

### 第二步：规划可复用内容

针对每个示例进行分析：

1. 思考从零开始如何完成任务
2. 找出反复执行这些任务时有帮助的脚本、参考资料和资产

示例：创建用于“帮我旋转这个 PDF”的 `pdf-editor` 技能时，可以发现：

1. 每次旋转 PDF 都需要重复编写相同代码
2. 因此适合提供 `scripts/rotate_pdf.py`

示例：创建用于“帮我做一个待办应用”或“做一个步数仪表盘”的 `frontend-webapp-builder` 技能时，可以发现：

1. 每次创建前端应用都需要相同的 HTML 或 React 样板
2. 因此适合提供 `assets/hello-world/` 模板

示例：创建用于“今天有多少用户登录”的 `big-query` 技能时，可以发现：

1. 每次查询都需要重新确认表结构和关系
2. 因此适合提供记录数据结构的 `references/schema.md`

根据所有示例整理技能需要的脚本、参考资料和资产。

### 第三步：初始化技能

只有技能目录已经存在时才跳过本步骤，并直接进入下一步。

从零创建技能时，运行 `init_skill.py`。该脚本会生成技能目录和所需模板，降低遗漏和格式错误的风险。

用法：

```bash
scripts/init_skill.py <skill-name> --path <output-directory> [--resources scripts,references,assets] [--examples]
```

示例：

```bash
scripts/init_skill.py my-skill --path skills/public
scripts/init_skill.py my-skill --path skills/public --resources scripts,references
scripts/init_skill.py my-skill --path skills/public --resources scripts --examples
```

脚本会：

- 在指定路径创建技能目录
- 生成带有正确前置元数据 frontmatter 和待办占位内容的 `SKILL.md`
- 根据 `--resources` 创建资源目录
- 使用 `--examples` 时添加示例文件

初始化后，根据需要完善 `SKILL.md` 并添加资源。使用了 `--examples` 时，替换或删除占位文件。

### 第四步：编辑技能

编辑新建或现有技能时，应始终考虑它将由另一个 Mind 实例使用。只提供对 Mind 有帮助且不显而易见的信息，重点补充过程知识、领域细节和可复用资源。

#### 编写可复用内容

先实现第二步识别出的 `scripts/`、`references/` 和 `assets/`。部分内容可能需要用户提供，例如品牌资产、模板或内部文档。

实际运行新增脚本，确认没有错误且输出符合预期。存在大量相似脚本时，测试有代表性的一部分即可。

使用了 `--examples` 时，删除不再需要的占位文件。只保留实际需要的资源目录。

#### 更新 SKILL.md

**写作要求：** 使用祈使或不定式表达，直接说明应执行的动作。

##### 前置元数据 frontmatter

YAML 前置元数据只写 `name` 和 `description`：

- `name`：技能名称
- `description`：技能的主要触发依据，帮助 Mind 判断何时使用技能
  - 同时说明技能能力和具体触发场景。
  - 所有“何时使用”的信息都写在这里，不要放在正文中。正文只有触发后才会载入。
  - `docx` 技能描述示例：“提供文档创建、编辑和分析能力，支持修订、批注、格式保留和文本提取。Mind 需要创建、修改或分析 `.docx` 文件时使用。”

不要在 YAML 前置元数据中加入其他字段。

##### 正文

编写技能及其随附资源的使用说明。

### 第五步：验证技能

技能开发完成后，运行验证脚本，尽早发现基础问题：

```bash
scripts/quick_validate.py <path/to/skill-folder>
```

验证脚本会检查前置元数据结构、必需字段和命名规则。验证失败时，修复报告的问题并重新运行。

### 第六步：迭代

用户通常会在实际使用后立即提出改进需求，此时上下文最完整。

**迭代流程：**

1. 在真实任务中使用技能
2. 记录执行困难或低效之处
3. 确定需要更新的 `SKILL.md` 或随附资源
4. 实施修改并重新测试
