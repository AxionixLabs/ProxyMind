# Routing Strategy

## 目标
链路分流用于判断用户任务应该走设备/UI 链路，还是非设备分析链路。

正确分流可以避免无意义的设备前置步骤，也能避免在 UI 操作前缺少状态收敛。

## 分流总则
用户要求中只要涉及以下内容，默认归入设备/UI 链路：

```text
设备
模拟器
APP 当前页面
点击
输入
滑动
滚动
启动 APP
关闭 APP
前后台切换
权限弹窗
录屏
截图采集
设备日志采集
在线状态采集
```

用户要求只基于已有材料分析时，归入非设备链路：

```text
已有日志
已有截图
已有录屏
已有测试报告
已有测试结果
已有 CSV / JSON / 文本文件
已有崩溃堆栈
```

## 设备/UI 链路

### 触发场景
以下任务必须走设备/UI 链路：

- 启动 APP
- 操作 APP 页面
- 点击按钮
- 输入账号、密码、搜索词、表单内容
- 滑动列表或页面
- 处理权限弹窗、系统弹窗、升级提示
- 检查当前页面是否正常
- 复现移动端问题
- 采集截图、录屏、设备日志
- 执行启动、前后台切换、长时间驻留等在线测试
- 依赖设备当前状态或 APP 当前页面的任务

### 标准链路
```text
Preflight
→ 确认页面锚点
→ 查找目标
→ 执行动作
→ 等待稳定
→ 采集最小证据
→ 输出结论
```

## 非设备链路

### 触发场景
以下任务归入非设备链路：

- 分析已有日志
- 总结已有截图
- 分析已有录屏
- 整理已有测试报告
- 对已有测试结果做归纳
- 提取崩溃、ANR、卡顿、错误码
- 输出问题结论、复现步骤、风险说明

### 标准链路
```text
识别输入材料
→ 提取关键事实
→ 归类问题
→ 输出结论和建议
```

### 禁止附加前置
非设备链路不得自动附加：

```text
连接设备
解锁屏幕
启动 APP
处理弹窗
获取当前页面
重新采集日志
```

除非用户明确要求重新采集。

## 串联链路
只有用户明确表达“先操作设备，再分析结果”时，才串联两类链路。

示例：

```text
打开 APP 录屏 3 分钟，然后分析卡顿现象
```

允许：

```text
设备/UI 链路
→ 采集录屏
→ 非设备分析
→ 输出结论
```

如果用户只说：

```text
分析这份录屏
```

则直接走非设备链路。

## 缺参处理
缺少关键参数时，只问一个最关键问题，不一次性列长清单。

优先级：

```text
平台：Android / iOS
→ 设备标识
→ APP 标识：package / bundle id
→ 目标页面或操作目标
→ 测试账号或测试数据
→ 输出要求
```

## 不确定时的处理
如果无法判断链路类型：

- 用户提到设备、页面、点击、输入、采集，优先按设备/UI 链路。
- 用户提到已有文件、日志、报告、录屏，优先按非设备链路。
- 两者都可能时，问一个最短问题确认是否需要实际操作设备。

示例：

```text
你是要我实际操作设备复现，还是只分析已有日志？
```
