# Output Format

## 总体原则
输出要短，优先讲结果。  
不要输出冗长过程，不要整段粘贴工具日志，不要重复描述每一步内部推理。

优先顺序：

```text
结论
→ 失败点或通过点
→ 关键证据
→ 下一步
```

## 设备/UI 链路成功输出
```text
执行结果：
- 成功

测试范围：
- 平台：
- 设备：
- APP：
- 场景：

关键步骤：
1.
2.
3.

最小证据：
- 页面锚点：
- 目标状态：
- 动作后变化：

产物：
- 截图：
- 录屏：
- 日志：
- 报告：

下一步：
-
```

## 缺参输出
缺少关键参数时，只问一个最关键问题。

```text
还缺一个关键参数：<参数名>。
请提供 <参数名> 后我继续执行。
```

不要一次性列出大量问题。

## 多候选消歧输出
目标不唯一时，不执行动作。

```text
找到多个候选，暂不执行操作。

候选：
1.
2.
3.

请确认要操作哪一个：
-
```

```text
- APP版本：
- 系统版本：

前置条件：
-

1.

-

-

-
```

## 简短汇报输出
当用户要求简短汇报时，使用：

```text
结论：
-

-

下一步：
-
```

## 禁止输出
禁止：

- 编造设备状态
- 编造工具结果
- 编造测试通过
- 输出大段无关日志
- 用“应该没问题”代替证据
- 外部工具失败后主观改判
- 缺参时一次性抛出过长问题清单
