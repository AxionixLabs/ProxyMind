# Nexus 示例对象

## What

这份文档不是再解释一遍 `Nexus` 是什么，而是提供一组稳定示例，教模型把接口任务写成“可执行、可回看、可验收、可回归”的自然语言说明。

它解决的是：

- 登录类接口任务怎么写得稳。
- 怎么同时写清通过条件和要回收的结果。
- 什么时候该先预览 / 校验，什么时候该直接执行。
- 多步回归怎么拆成可复用样例。

## When To Use

- 你已经知道要做接口测试，但想把任务写得更可验收。
- 你要拿到 token、trace_id、user_id 这类后续产物。
- 你要明确通过条件，而不是只说“看下是否成功”。
- 你要把多步接口链路固化成批量回归材料。

## Core Rules

- 对外最终输出，尽量写 `mind ...` 命令和自然语言任务。
- 稳定样例至少要区分：这次真正要发的内容、通过条件、要回收的结果、会变化的动态值。
- 动态变量复杂时，优先先做预览或校验。
- 多步链路优先拆成共享部分和多个独立样本。
- 如果把这些样例固化进 `--code` 文件，任务块边界统一按 [`--code` 星图写法](blueprint.md) 执行。
- 对齐当前客户端工具集时，要把“单次执行”“批量回放”“只预览”“只校验”区分开，不要混成一个抽象动作。
- 稳定策略仍然是：当前要发的内容单独写，共享默认值放在共享层，动态值集中管理，批量回放拆成多个样本；但对外示例应保持高层可读。

## Good Examples

自然语言写法：

```bash
mind --fast --mcp "对 https://api.example.com/login 做 POST，请求体包含 username 和 password，校验状态码 200，断言 response.body_json.ok=true，拿到 token、user_id 和 trace_id，并返回摘要。"
```

稳定样例：

```text
登录类请求：
- 写清请求方法、接口地址、必要请求头和入参
- 写清通过条件：先看状态码，再看业务成功标记
- 写清要回收的关键结果：例如 token、user_id、trace_id
- 最后要求返回摘要，而不是只回一句“成功”
```

批量回归样例：

```text
批量 profile 回放：
- 共享层里放 base_url、公共请求头和整批复用的鉴权材料
- 每条样本只保留自己的差异内容和个别通过条件
- 并发和失败策略单独声明，不混进单条请求描述
- 输出时既要有每条样本的结果，也要有总体通过率和失败清单
```

星图文件提醒：

```text
如果你把这些接口样例写进 `--code` 文件，直接按 `--code` 星图规范写任务块；不要在这里重新发明一套分隔规则。
```

补充示例：

```bash
mind --fast --mcp "先只校验这组 HTTP 回归样本的结构是否完整：公共鉴权头放在共享层，每条样本只保留自己的差异内容；检查并发设置和失败策略是否合理，返回展开后的预览摘要，不实际发请求。"
```

```bash
mind --fast --mcp "先发送登录请求并拿到 token；再用这个 token 访问 profile 和 order 接口；分别校验状态码和业务字段，返回每一步拿到的结果、最终结论和失败步骤。"
```

```bash
mind --fast --mcp "对 websocket 地址建立连接，发送一条启动消息；拿到第一条返回里的 job_id，再校验最后一条消息里的状态为 success，返回消息摘要。"
```

## Bad Examples

```bash
mind --fast --mcp "测一下登录接口。"
```

问题：

- 没说请求方法、目标和入参。
- 没说通过条件。
- 没说要回收什么关键结果。

```text
把批量回归固化进 `--code` 文件，却没有按星图规范处理任务块边界。
```

问题：

- 容易漏掉块结束符。
- 继续追加样本时，内容容易串块。

```bash
mind --fast --mcp "把这一批接口都跑一下，能跑就行。"
```

问题：

- 没区分共享部分和单条样本的差异。
- 没写并发和失败策略。
- 没写最终要返回逐条结果还是总体汇总。

```bash
mind --fast --mcp "先帮我看看请求长什么样，再顺手发出去。"
```

问题：

- 把“执行前预览/校验”和“真实执行”混成一个动作。
- 不利于在失败时判断是结构问题还是执行问题。

## Checklist

- 是否区分了当前要发的内容、通过条件、要回收的结果。
- 是否先判断状态，再判断业务成功，再判断关键结果存在。
- 多步链路是否拆成多个独立样本。
- 动态变量复杂时是否先做预览或校验。
- 示例是否仍然面向人可读，并且清楚区分了执行、校验和回放这几类策略。

## Failure Handling

- “通过条件”和“要回收的结果”混用时，先把两者拆开写。
- 样例复杂时，先做预览或校验，避免直接执行后难以定位。
- 鉴权链路复杂时，不要把签名、JWT、请求发送全写成一句话；拆成“准备材料、生成鉴权结果、带着鉴权去发请求”更稳。
- 批量回归失败时，不要只给总失败；至少返回失败样本、失败原因和是否中断后续样本。

## 结果回收

### 结果回收要解决什么问题

结果回收不是为了“多拿几个字段”，而是为了把后续真正要用的产物拿出来。

最常见的是：

- token
- trace_id
- user_id
- order_id
- job_id
- 最终状态

### 怎么写得像人话

高层自然语言里，通常这样表达：

- 拿到 token，供后续鉴权复用
- 拿到 trace_id，便于排查失败样本
- 拿到 order_id，供下一步查询订单详情
- 拿到 job_id，并在后续轮询里继续使用

### 最佳实践

- 只提后面真要用的值。
- 回收的字段要有用途，不要为了“看起来完整”而堆太多字段。
- 这些结果是为了回看和传递，不是为了表达通过条件。
- 需要判断通过还是失败时，优先写成通过条件。

### 自然语言版本举例

```bash
mind --fast --mcp "发登录请求，拿到 token 和 uid，供下一步访问用户资料接口使用。"
```

```bash
mind --fast --mcp "连接 websocket，拿到第一条消息里的 job_id，并确认最后一条消息里的状态，返回消息摘要。"
```

## 鉴权用法

## 先说边界

`Nexus` 本身不是一个“自动鉴权黑盒”。

它的真实做法是：

- 简单鉴权材料直接带着去发请求
- 动态值先准备好再发请求
- 复杂 JWT / HMAC / RSA / AES 计算，优先交给安全工具
- 算出来的结果再回填到接口请求里

所以要这样理解：

- `Nexus` 负责“带着鉴权材料去发请求”
- 安全工具负责“把鉴权材料算出来”

### 方式一：静态 Bearer Token

```bash
mind --fast --mcp "发送 GET https://api.example.com/profile，请求头带 Authorization: Bearer demo-token，校验状态码 200，并返回摘要。"
```

### 方式二：动态 Bearer Token

```bash
mind --fast --mcp "先请求登录接口并拿到 token；再发送 GET https://api.example.com/profile，请求头带这个 token；校验状态码 200，并返回拿到的结果与摘要。"
```

这种方式适合：

- token 来自上一步提取结果
- token 来自共享变量或环境变量
- 同一批请求复用一个 token

### 方式三：Basic 认证

```bash
mind --fast --mcp "发送 GET https://api.example.com/profile，使用 Basic 认证；校验状态码 200，并返回摘要。"
```

### 方式四：Cookie / Session 鉴权

```bash
mind --fast --mcp "发送 GET https://api.example.com/profile，请求头带已有 Cookie 和 Session 信息，校验状态码 200，并返回摘要。"
```

### 方式五：API Key / 自定义头

```bash
mind --fast --mcp "发送 GET https://api.example.com/profile，请求头带 X-App-Id 和 X-Api-Key，校验状态码 200，并返回摘要。"
```

### 方式六：签名鉴权

签名鉴权通常分成三步，不要混成一句“自动签名”：

1. 先准备时间戳、nonce、请求体摘要或签名原文
2. 再调用安全能力生成签名结果
3. 最后带着签名头去发请求

典型写法：

```bash
mind --fast --mcp "先准备时间戳、nonce 和签名原文；再生成 HMAC 签名；然后发送支付接口请求，请求头带 X-App-Id、X-Timestamp、X-Nonce、X-Sign；校验状态码 200 和支付状态为成功，并提取 trace_id。"
```

### 方式七：JWT 鉴权

```bash
mind --fast --mcp "先生成 HS256 JWT；再发送 GET /profile，请求头带 Authorization: Bearer 这个 token；校验状态码 200，并返回摘要。"
```

### 鉴权最佳实践

- 静态 token 直接带头里。
- 动态 token 优先先拿到再复用。
- 共享鉴权材料放在共享层理解，不要每条样本重复写。
- 单条样本的差异字段只放到当前请求里。
- 复杂签名不要硬塞进一段长描述，优先拆成“准备材料 + 安全计算 + 发请求”。

## 动态变量用法

### 动态变量要解决什么问题

动态变量的价值不是“写表达式”，而是把会变化的值单独拎出来，避免每条请求重复改。

最常见的场景是：

- 用户名、密码、租户 ID
- token
- 请求 ID
- 时间戳
- nonce

### 怎么理解

- 动态变量：放你想显式命名、显式复用的值
- 共享层：放公共默认值
- 当前请求：放这一次真正要发的内容

如果是批量：

- 共享层放公共默认值
- 每条样本只放自己的差异内容
- 动态变量是整批共享，不会按样本自动切换

### 最佳实践

- 动态变量层负责准备材料，不负责做重型安全计算。
- 适合放时间戳、nonce、请求 ID、租户 ID、公共鉴权材料。
- 不适合把完整 HMAC、JWT、RSA、AES 都塞成一大段模板表达。
- 复杂安全链路优先拆成模板层加安全工具两步。

### 自然语言版本举例

```bash
mind --fast --mcp "先只预览这份请求，确认 tenant、token 和请求 ID 都能被正确展开；返回展开后的请求摘要，不实际发请求。"
```

```bash
mind --fast --mcp "校验这组批量样本里，每条样本是否都只保留自己的差异内容，共享 token 和公共头是否已经正确放在共享层；返回校验结论，不实际执行。"
```

### SSE batch 特别注意

这类规则很容易写错，所以单独记住：

- 每条样本的用户输入要放在各自的内容里，不要写成全局共享值
- 每条样本的当前时间也要放在各自的内容里
- 如果后一条样本依赖前一条样本的回收结果，执行时就不要并发跑

## 四块能力如何串成一个闭环

最常见的完整链路是这样：

1. 先准备动态值
2. 必要时先做鉴权材料准备
3. 发请求
4. 拿到 token、trace_id、result_id 等产物
5. 用通过条件判定是否通过

### 闭环一：登录后提取 token

```bash
mind --fast --mcp "发送 POST https://api.example.com/api/login，请求体带 username 和 password；断言状态码 200 和业务成功；拿到 token，返回摘要。"
```

### 闭环二：带 Bearer token 访问受保护接口

```bash
mind --fast --mcp "先请求登录接口并拿到 token；再发送 GET https://api.example.com/profile，请求头带这个 token；断言状态码 200 和 ready 字段为 true；返回每一步摘要。"
```

### 闭环三：签名请求

```bash
mind --fast --mcp "先准备 ts、nonce 和签名原文；再计算 HMAC 签名；然后发送支付接口请求，请求头带签名相关字段；断言状态码 200 和支付状态为成功，并拿到 trace_id。"
```

## 最后再记一遍边界

- 通过条件：判定是否通过
- 回收结果：取出要回看或传递的字段
- 动态变量：准备会变化的值
- 鉴权：简单场景直接带着去发请求，复杂场景配合安全工具

如果你只想先看请求长什么样，用“先预览展开结果”的自然语言写法。

如果你想先查字段是不是合法，用“先做结构校验”的自然语言写法。

如果你真的要发请求，再明确写“执行这个请求”或“执行这批回放”。
