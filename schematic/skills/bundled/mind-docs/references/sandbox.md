# Sandbox 场景

## What

`Sandbox` 负责把一段代码或一个小项目交给云端环境执行，并把结果带回来。

它不是当前本地工具集里的直接执行入口；通常由云端注入能力或本地 shell 策略的云端沙箱接管来完成。写任务时要把云端依赖和不可用时的回报讲清楚。

它关心的不是底层参数，而是：

- 跑什么。
- 输入来自哪里。
- 成功时返回什么。
- 失败时怎样收束。

## When To Use

- 执行脚本。
- 处理 CSV / JSON / 日志数据。
- 运行多文件小项目。
- 获取 stdout、退出码和产物路径。

## When Not To Use

- 只需要本地代码修改或仓库分析，不需要远端执行环境。
- 只是想描述实现思路，没有明确输入和产出。
- 任务本身是接口验证或设备巡检，应转到对应 playbook。

## Decision Table

| 任务形态 | 推荐写法重点 |
| --- | --- |
| 单文件脚本处理数据 | 写清输入文件、目标统计和 stdout 摘要 |
| 多文件小项目执行 | 写清入口、退出码、关键输出、产物路径 |
| 可能超时或长耗时任务 | 明确超时后如何终止、返回哪些中间结果 |
| 依赖云端能力但可能不可用 | 补“若不可用则如何回报或替代” |

## Core Rules

- 对外只描述任务目标和结果要求。
- 不写底层执行参数与内部字段细节。
- 说明代码任务目标、输入来源、期望结果、异常要求。
- 最终产出至少应包含状态、关键输出和产物路径摘要。
- 如果是多文件项目，尽量写清入口和预期成功标志。
- 如果产物重要，明确要求返回产物路径，而不是只看 stdout。

## Good Examples

```bash
mind --chat "在云端 sandbox 执行一段 Python 脚本，读取 sales.csv，按城市聚合成交额并输出 Top5；完成后返回运行状态、stdout 摘要和产物路径。"
```

```bash
mind --chat "在云端 sandbox 运行一个多文件小项目，入口为命令行程序；完成后返回退出码、关键输出、产物路径和失败原因。"
```

```bash
mind --chat "在云端 sandbox 执行一段 Python 脚本，读取 logs.jsonl，按 error_type 聚合并输出 TOP10 错误分布；完成后返回状态、stdout 摘要和生成文件路径。"
```

## Bad Examples

```bash
mind --chat "跑一下 python。"
```

问题：

- 没说输入。
- 没说目标。
- 没说产出。

```bash
mind --chat "在云端跑一下这个项目，能跑就行。"
```

问题：

- 没有入口和成功标准。
- 没有失败回报。
- 没有产物要求。

## Checklist

- 是否写清任务目标。
- 是否写清输入文件、目录或脚本文本。
- 是否写清产出、退出码和失败回报。
- 是否考虑云端依赖不可用时的处理方式。
- 是否明确项目入口或脚本输入。

## Failure Handling

- 超时或失败时，返回当前进度、错误信息和已生成产物。
- 云端不可用时，明确说明依赖缺失，并在可能时给出本地替代方案。
- 多文件项目运行失败时，优先返回入口、退出码、最后关键输出和已生成产物。
