# Coding 场景

## What

`Coding` 负责把代码修改任务写成最小可执行补丁，而不是模糊地“顺手修一下”。

它最关心：

- 改哪一块。
- 不该碰哪一块。
- 怎么验证。
- 最后怎么交付。

## When To Use

- Bug 修复。
- 补测试。
- 局部重构。
- 风险收敛和结果收束。

## Decision Table

| 任务特征 | 推荐写法重点 |
| --- | --- |
| 只修一个问题 | 写清模块范围和不变契约 |
| 需要补测试 | 写清覆盖的 case 和验证命令 |
| 风险较高 | 写清不要改的边界和待确认项 |

## Core Rules

- 明确改动范围：模块、目录、接口、页面。
- 明确约束：不要改无关模块、只做最小修复、保持对外契约不变。
- 明确验证：跑哪些测试、看哪些输出、无法验证时如何报告。
- 明确产出：改动文件、验证结论、风险点、待确认项。
- 使用策略要与当前工具集对齐：编码能力是工作区内批量 shell 命令、文本写入和 unified diff patch；不要把它写成另一个会话式黑盒。
- Shell 命令用于诊断、测试、构建或脚本执行；创建/覆盖文本文件和局部补丁应写成工作区文件写入或 patch 任务。
- 示例应强调工作目录、改动边界、验证方式和收束产出，而不是展开底层参数清单。

## Good Examples

```bash
mind --xtra "只修改登录链路相关代码，修复空指针问题；保持接口字段和返回结构不变；补最小回归测试；完成后返回改动文件、验证结果和剩余风险。"
```

```bash
mind --xtra "为 /mcp 文档接口补一组最小契约测试，覆盖匿名访问、tools/list、tools/call 和 resources/read；不要改无关路由。"
```

补充示例：

```bash
mind --xtra "在当前工作区只修改登录链路相关代码；先用只读命令定位空指针来源，再用最小补丁修复；保持接口字段和返回结构不变；补最小回归测试；完成后返回改动文件、验证结果和剩余风险。"
```

```bash
mind --xtra "在 /mcp 文档接口目录补最小契约测试，覆盖匿名访问、tools/list、tools/call 和 resources/read；不要改无关路由；完成后运行对应测试并给出验证结论和未覆盖风险。"
```

## Bad Examples

```bash
mind --xtra "修一下登录。"
```

问题：

- 没有范围。
- 没有保持不变的契约。
- 没有验证和交付要求。

## Checklist

- 是否写清改动范围。
- 是否写清不允许改动的部分。
- 是否指定验证方式。
- 是否要求返回改动摘要、验证结果和风险。
- 示例是否仍然是面向人的任务描述，而不是参数化调用对象。

## Failure Handling

- 无法验证时，要明确写出未验证项和原因。
- 发现需求涉及多个无关模块时，应收窄范围或拆分任务。
