# 云端与本地边界

## What

这份文档负责解释能力来源，而不是解释某个具体工具怎么叫。

只用两种外部语义：

- 本地执行能力：依赖本地环境、本地资源、本地注册能力。
- 云端注入能力：依赖服务端可用性、会话配置、托管侧注入。

Builtin 事件名或 Hosted 工具名可以存在于系统内部，但不是对外稳定接口。

当前项目能力来源主要分三类：

- Mind native：shell 命令、持续命令会话、工作区文本写入、unified diff patch，以及 Mind 侧内置 coding 工具。
- External MCP：用户在 `mcp_servers.json` 配置并由 Mind 连接的第三方 MCP 服务。
- Helix provider：官方垂直领域 MCP 服务，覆盖接口/设备/媒体/性能等执行面；需要 `--mcp` 或 REPL `/helix-link` 后才挂载。
- Xtra 只聚合 Mind native 与 External MCP，不包含 Helix MCP。

Mind 顶层随包路由的本地二进制工具只按 Mind native 语义上报，例如 `rg`、`jq`、`ast-grep`。Helix provider 自身依赖的 `adb`、`ffmpeg`、`ffprobe`、`k6`、`framix`、`memrix` 不作为 Mind 顶层工具承诺。

## When To Use

- 你需要判断一项能力是否能在本地直接完成。
- 你怀疑一条任务依赖云端注入能力。
- 你要给任务补一条稳定降级路径。

## When Not To Use

- 你已经知道当前任务完全是本地文件读写或本地代码修改，这时不需要重复讨论云端边界。
- 你正在设计某个具体场景的任务模板，这时应优先去对应 playbook。

## Decision Table

| 现状 | 推荐写法 |
| --- | --- |
| 来源明确且本地可跑 | 直接写任务目标，不展开内部名词 |
| 来源明确但依赖云端 | 明确依赖条件和产出要求 |
| 来源不确定 | 只写意图，不猜内部能力名 |
| 云端可能不可用 | 写清“若不可用则如何回报或替代” |
| 任务可以本地等价完成，但用户要求的是结果而非来源 | 仍然优先写意图，不强调内部来源 |
| 任务明显需要远端执行环境、会话态或托管注入 | 把依赖条件写清，并补失败降级 |
| 本地 shell 命令被策略判定需要云端沙箱 | 写清云端依赖、期望 stdout/产物和不可用时的回报 |
| 任务需要官方垂直领域 MCP 能力 | 使用 `--mcp` 或提示先 `/helix-link`，并说明 Helix 不可用时如何回报 |

## Core Rules

- 对外表述尽量使用 `mind ...` 和自然语言任务。
- 不暴露 `builtin`、`hosted tool`、内部事件名作为最终接口。
- 来源不确定时，优先表达“要做什么”，不要表达“调用哪个内部能力”。
- 云端依赖明显时，最好同时给出本地替代方案或失败回报。
- 不要把“能不能用某个内部能力”写成主任务；主任务永远是业务意图和交付结果。
- 说明依赖时，用“本地执行能力 / 云端注入能力”这组稳定语义。
- 说明 Helix 时，用“官方垂直领域 MCP provider”这组稳定语义，不把它写成 Mind 默认执行前置条件。

## Good Examples

```bash
mind --xtra "查找 Mind CLI 的运行模式和常用命令，返回最短可执行示例。"
```

```bash
mind --xtra "如果云端能力可用，执行一次远端 sandbox Python 数据分析；若不可用，明确说明依赖缺失并给出本地可替代做法。"
```

```bash
mind --xtra "查找关于 Mind 文档中心的模式选择规则；若云端文档能力不可用，则返回本地已知规则摘要和缺失项。"
```

## Bad Examples

```bash
mind --xtra "调用 hosted tool 查文档。"
```

```bash
mind --xtra "用 builtin 搜索一下。"
```

问题：

- 把内部能力名暴露成了外部协议。
- 对用户没有稳定语义。
- 云端不可用时没有降级路径。

```bash
mind --xtra "先确认能不能调用 builtin，再决定做什么。"
```

问题：

- 把内部可用性检查放到了任务中心。
- 没有真正的业务目标和交付要求。

## Checklist

- 是否只写了意图和结果要求。
- 是否避免暴露内部能力名。
- 是否在来源不确定时保持了中性表达。
- 是否为云端依赖写了可执行的回报或替代方案。
- 是否把来源边界写成了“条件”，而不是把内部能力名写成“目标”。

## Failure Handling

- 云端不可用时，明确说明依赖缺失。
- 能降级到本地等价任务时，优先给出本地替代方案。
- 无法降级时，至少返回失败原因、已知依赖和下一步建议。
- 如果来源不确定，不要硬判断；保持中性表达并把失败条件前置到任务里。
