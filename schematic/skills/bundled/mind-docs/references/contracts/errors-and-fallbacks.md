# 错误与回退

## What

这份文档定义失败时该怎样回报、怎样降级、怎样保持任务仍然可交付。

它关心的不是“报错字符串长什么样”，而是：

- 错误能否被定位。
- 已尝试动作是否可复盘。
- 下一步建议是否可执行。

## When To Use

- 输入缺失、来源不可读、前置条件不全。
- 云端能力不可用，需要考虑本地替代。
- 任务已经失败，但仍然需要输出可执行结论。

## When Not To Use

- 任务仍未执行，只是在设计正常路径，此时应优先写清正向目标和验收标准。
- 你只是想堆更多报错字符串，而不是提供可执行的回退方案。

## Decision Table

| 失败类型 | 首选动作 |
| --- | --- |
| URL 来源失败 | 回退本地文件 |
| 本地文件失败 | 回退 `inline` |
| 云端能力不可用 | 尝试本地等价任务或说明依赖缺失 |
| 校验条件缺失 | 明确指出缺的阈值、字段或前置条件 |
| 无法继续降级 | 返回失败原因、已尝试动作、下一步建议 |
| 多步任务中途失败 | 返回失败步骤、已保留证据、是否继续收束 |

## Core Rules

- 失败时不要只给一句“执行失败”。
- 失败回报至少包含：原因、已尝试、建议下一步。
- 能回退时要按稳定顺序回退，不要乱跳。
- 回退后仍要保留证据和上下文。
- 对多步骤任务，失败要落到具体步骤，而不是只给总失败。
- 回退方案要可执行，不能只是“请重试”。

## Good Examples

```text
本次执行失败：`nightly.md` 文件不存在，无法作为 `--code` 来源。
已尝试：读取本地文件 `nightly.md`。
建议下一步：确认文件路径是否正确，或改用 `mind --chat --code "inline:# name: smoke\n..."`。
```

```text
本次执行失败：压测目标已给出，但缺少通过阈值，无法判断是否达标。
已尝试：解析请求目标与时长参数。
建议下一步：补充失败率、P95 或吞吐阈值，例如“失败率低于 1%，P95 小于 300ms”。
```

```text
本次执行失败：登录巡检在“提交登录表单后等待首页标题出现”这一步超时。
已尝试：保留当前页面截图并导出日志。
建议下一步：检查测试账号是否有效，或补充首页成功标识是否已变更。
```

## Bad Examples

```text
失败了，请重试。
```

问题：

- 没有原因。
- 没有已尝试动作。
- 没有下一步建议。

```text
执行失败，可能是环境问题。
```

问题：

- 原因不具体。
- 没有给出已知依赖和下一步动作。

## Checklist

- 是否明确失败原因。
- 是否记录已尝试动作。
- 是否按稳定顺序回退。
- 是否给出用户现在就能执行的下一步。
- 是否保留证据路径或上下文。
- 多步骤失败时，是否指出具体失败步骤。

## Failure Handling

推荐回退顺序：

1. URL 失败回退本地文件。
2. 本地文件失败回退 `inline`。
3. 云端不可用时降级本地等价任务。
4. 仍失败时返回原因、已尝试、下一步建议。

对多步骤任务，补一条局部规则：

1. 标出失败步骤。
2. 保留当前证据。
3. 决定是否继续做收束动作。
4. 返回局部失败而不是抽象总失败。
